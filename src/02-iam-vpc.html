요소설명실무 원칙

3.2 정책 문서 해부

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadOwnBucketOnlyFromCorpNetwork",
      "Effect": "Allow",                        // Allow 또는 Deny
      "Action": ["s3:GetObject", "s3:ListBucket"],  // 서비스:API
      "Resource": [
        "arn:aws:s3:::my-study-bucket",          // ListBucket은 버킷 ARN
        "arn:aws:s3:::my-study-bucket/*"         // GetObject는 객체 ARN
      ],
      "Condition": {
        "IpAddress": { "aws:SourceIp": "203.0.113.0/24" },
        "Bool": { "aws:SecureTransport": "true" }
      }
    }
  ]
}

ARN 형식: arn:partition:service:region:account-id:resource. 예: arn:aws:ec2:ap-northeast-2:123456789012:instance/i-0abc. IAM·S3처럼 글로벌 성격의 서비스는 region/account 부분이 비어 있을 수 있습니다.

정책의 종류

정책 유형붙는 곳역할
자격 증명 기반 정책사용자, 그룹, 역할"이 주체는 무엇을 할 수 있다" — 권한 부여
리소스 기반 정책S3 버킷, SQS, KMS 키, Lambda 등"누가 이 리소스에 접근할 수 있다" — Principal 필드 있음, 크로스 계정 허용 가능
권한 경계(Permissions Boundary)사용자, 역할부여 가능한 최대 권한의 상한선(권한 부여 아님)
SCP / RCPOrganizations OU·계정계정 전체의 최대 권한 상한선(주체 기준 / 리소스 기준)
세션 정책AssumeRole 호출 시 전달해당 세션 권한을 추가로 축소
ACLS3(레거시) 등가급적 비활성화(S3 Object Ownership: Bucket owner enforced)

3.3 정책 평가 로직 [SAA]

그림 3-1. 단순화한 IAM 정책 평가 흐름: 명시적 Deny가 항상 이긴다
  • 기본은 거부(루트 제외). 허용하려면 반드시 Allow가 있어야 합니다.
  • 명시적 Deny는 모든 Allow를 이긴다.
  • SCP·권한 경계·세션 정책은 "교집합"으로 작동합니다. 이들 자체는 권한을 주지 않습니다.
  • 같은 계정 안에서는 자격 증명 정책 또는 리소스 정책 중 하나만 허용해도 됩니다. 크로스 계정에서는 양쪽 모두(호출자 계정의 자격 증명 정책 + 대상 리소스 정책) 허용해야 합니다.

3.4 역할(Role)과 STS

역할에는 두 가지 정책이 붙습니다. 신뢰 정책(Trust Policy)은 "누가 이 역할을 맡을 수 있는가", 권한 정책은 "맡은 뒤 무엇을 할 수 있는가"입니다.

// 신뢰 정책: EC2 서비스가 이 역할을 맡을 수 있음
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

EC2에 역할을 붙이면 인스턴스 프로파일을 통해 인스턴스 메타데이터(http://169.254.169.254)에서 임시 자격 증명이 자동으로 발급·갱신됩니다. SDK와 CLI는 이를 자동으로 사용합니다.

⚠ IMDSv2 강제SSRF 취약점으로 메타데이터의 자격 증명이 탈취되는 사고(대표적으로 2019년 Capital One 사건)를 막기 위해, 토큰 기반의 IMDSv2만 허용(HttpTokens=required)하고 홉 제한을 1~2로 설정하세요. 신규 인스턴스 기본값으로 계정 수준에서 강제할 수 있습니다.
# IMDSv2로 메타데이터 조회
TOKEN=$(curl -sX PUT "http://169.254.169.254/latest/api/token" \
        -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
     http://169.254.169.254/latest/meta-data/iam/security-credentials/
# 크로스 계정 역할 맡기
aws sts assume-role --role-arn arn:aws:iam::222233334444:role/ReadOnly \
    --role-session-name study --external-id my-ext-id

External ID는 제3자 SaaS가 고객 계정의 역할을 맡을 때 "혼동된 대리인(confused deputy)" 문제를 막기 위해 신뢰 정책 조건에 넣는 값입니다.

3.5 멀티 계정 전략: Organizations, SCP, Control Tower

규모가 커지면 "하나의 계정에 모든 것"이 아니라 계정을 경계로 분리합니다. 계정은 가장 강력한 격리 단위(권한·한도·비용·장애 범위)입니다.

Root (관리 계정: 결제·조직 관리만, 워크로드 금지)
 ├── OU: Security    → Log Archive 계정, Security Tooling(Audit) 계정
 ├── OU: Infrastructure → Network 계정(TGW, DX, 공용 VPC), Shared Services
 ├── OU: Workloads
 │     ├── OU: Prod  → app-prod 계정 …
 │     └── OU: Dev   → app-dev 계정 …
 └── OU: Sandbox     → 개인 실험 계정 (예산 제한)
// SCP 예: 허용된 리전(서울, 버지니아) 외에서는 모든 작업 거부 (글로벌 서비스 예외)
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyOutsideAllowedRegions",
    "Effect": "Deny",
    "NotAction": ["iam:*", "organizations:*", "route53:*", "cloudfront:*",
                  "sts:*", "support:*", "budgets:*", "waf:*"],
    "Resource": "*",
    "Condition": { "StringNotEquals": {
      "aws:RequestedRegion": ["ap-northeast-2", "us-east-1"] } }
  }]
}
  • SCP는 관리 계정에는 적용되지 않습니다. 그래서 관리 계정에는 워크로드를 두지 않습니다.
  • Control Tower: 위 구조(랜딩 존), 가드레일, 계정 자동 발급(Account Factory)을 자동 구성해주는 서비스.
  • IAM Identity Center: 사내 IdP(Entra ID, Okta, Google 등)와 연동해 여러 계정에 SSO. 권한 세트(Permission Set)가 각 계정의 역할로 배포됩니다.
💡 최소 권한을 찾는 도구IAM Access Analyzer: 외부에 공유된 리소스 탐지, CloudTrail 기반 정책 생성, 미사용 권한·역할 탐지. 마지막 액세스 정보(Last accessed)로 쓰지 않는 서비스 권한을 제거하세요.
📝 확인 문제 3 1) 사용자 정책에 s3:* Allow, 그룹 정책에 s3:DeleteBucket Deny가 있습니다. 버킷 삭제가 가능한가요?
2) 계정 A의 Lambda가 계정 B의 S3 버킷을 읽으려 합니다. 어디에 무엇을 설정해야 하나요(두 가지 방법)?
3) SCP에서 EC2를 허용했지만 사용자에게 아무 정책도 없습니다. 이 사용자는 EC2를 쓸 수 있나요?

CHAPTER 4VPC 기본

학습 목표 · VPC CIDR을 겹치지 않게 설계한다 · 퍼블릭/프라이빗 서브넷의 정확한 정의를 말한다 · IGW, NAT Gateway를 통한 패킷 흐름을 그린다 · 보안 그룹과 NACL을 구분해 적용한다

4.1 VPC란

VPC(Virtual Private Cloud)는 AWS 안에 만드는 논리적으로 격리된 나만의 네트워크입니다. 하나의 리전에 속하며, 그 리전의 모든 AZ에 걸쳐 존재합니다. 서브넷은 하나의 AZ에만 속합니다.

그림 4-1. 2개 AZ에 걸친 표준 3계층 VPC 구조

VPC CIDR 규칙

  • IPv4 CIDR 크기는 /16 ~ /28. 기본 CIDR 외에 보조 CIDR을 추가할 수 있습니다(기본 한도 5개, 증가 요청 가능).
  • 한 번 만든 기본 CIDR은 변경 불가 → 처음부터 넉넉하고 겹치지 않게 설계하는 것이 매우 중요합니다.
  • Peering/TGW/VPN으로 연결될 가능성이 있는 모든 네트워크(다른 VPC, 온프레미스, 협력사)와 CIDR이 겹치면 직접 라우팅이 불가합니다.
  • 대규모 조직은 VPC IPAM으로 계정·리전별 IP 풀을 중앙 관리합니다.
💡 CIDR 설계 예시 (조직 전체)10.0.0.0/8을 나눠 사용: 온프레미스 10.0.0.0/12, AWS 서울 10.16.0.0/12(그 안에서 VPC마다 /16 또는 /20), AWS 버지니아 10.32.0.0/12… 이렇게 리전별로 요약(summarize) 가능하게 잡으면 라우팅 테이블이 단순해집니다.

4.2 서브넷

각 서브넷에서는 5개의 IP가 예약되어 사용할 수 없습니다. 10.0.1.0/24 기준:

주소용도
10.0.1.0네트워크 주소
10.0.1.1VPC 라우터
10.0.1.2DNS 서버(Route 53 Resolver) — 정확히는 VPC 기본 CIDR의 베이스+2
10.0.1.3향후 사용을 위해 예약
10.0.1.255브로드캐스트 주소(VPC는 브로드캐스트 미지원이지만 예약)

퍼블릭 서브넷 vs 프라이빗 서브넷 — 정확한 정의

서브넷 자체에 "퍼블릭" 속성이 있는 것이 아닙니다. 연결된 라우트 테이블에 0.0.0.0/0 → igw-xxx 경로가 있으면 퍼블릭 서브넷입니다. 인스턴스가 실제로 인터넷과 통신하려면 추가로 퍼블릭 IP 또는 Elastic IP가 있어야 합니다.

구분기본 경로인바운드(인터넷→)아웃바운드(→인터넷)
퍼블릭IGW가능(퍼블릭 IP + SG 허용 시)가능
프라이빗 (NAT)NAT Gateway불가가능(NAT 경유)
격리(Isolated)없음불가불가 (VPC 엔드포인트로만 AWS 서비스 접근)

4.3 라우트 테이블

  • 모든 VPC에는 메인 라우트 테이블이 있고, 명시적으로 연결하지 않은 서브넷은 메인을 사용합니다. → 실수 방지를 위해 메인은 프라이빗 상태로 두고, 서브넷마다 명시적으로 연결하세요.
  • local 경로(VPC CIDR)는 삭제할 수 없으며, VPC 안의 모든 서브넷은 기본적으로 서로 통신 가능합니다. (더 구체적인 경로로 미들박스를 경유하게 만드는 것은 가능)
  • 하나의 서브넷은 하나의 라우트 테이블에만 연결되며, 하나의 라우트 테이블은 여러 서브넷에 연결될 수 있습니다.
  • 대상(target) 종류: local, IGW, NAT GW, ENI/인스턴스, VPC Peering, TGW, VGW, 게이트웨이 엔드포인트(프리픽스 리스트), GWLB 엔드포인트, Egress-only IGW 등.
  • 게이트웨이 라우트 테이블(Ingress Routing): IGW/VGW에 라우트 테이블을 연결해, 들어오는 트래픽을 방화벽 어플라이언스로 먼저 보낼 수 있습니다.

4.4 인터넷 게이트웨이 (IGW)

  • VPC당 1개만 연결, 수평 확장·고가용성이 기본 제공(관리할 것 없음, 대역폭 제한 없음, 비용 없음).
  • 퍼블릭 IPv4를 가진 인스턴스에 대해 사설 ↔ 공인 IP의 1:1 NAT 수행.
  • IPv6에서는 NAT 없이 라우팅만 수행합니다.

4.5 NAT Gateway

특징내용
배치퍼블릭 서브넷에 생성(퍼블릭 NAT), Elastic IP 연결. 프라이빗 서브넷 라우트 테이블에 0.0.0.0/0 → nat-xxx
가용성AZ 단위 리소스. AZ 장애 대비를 위해 AZ마다 하나씩 두고, 각 AZ 프라이빗 서브넷은 같은 AZ의 NAT를 사용 (AZ 간 데이터 전송 비용도 절감). 2025년 출시된 리전 NAT Gateway 모드는 하나의 NAT로 여러 AZ에 자동 확장되므로 신규 구성 시 검토하세요.
성능5 Gbps에서 시작해 100 Gbps까지 자동 확장. 목적지(IP:포트:프로토콜)당 동시 연결 55,000개 — 초과 시 EIP 추가(최대 8개)
보안보안 그룹을 붙일 수 없음(NACL로 제어). 인바운드로 시작되는 연결은 받지 않음
비용시간당 요금 + 처리 GB당 요금 → S3/DynamoDB 트래픽은 게이트웨이 엔드포인트로 우회해 비용 절감
프라이빗 NATEIP 없이 사설 IP로 NAT. 겹치는 CIDR 간 통신, 온프레미스로 나갈 때 IP 대역 통일 등에 사용
ℹ NAT 인스턴스EC2에 NAT를 직접 구성하는 레거시 방식. 비용은 저렴하지만 가용성·확장을 직접 관리해야 하며, 소스/대상 확인(Source/Dest Check)을 비활성화해야 동작합니다. 시험에서는 "관리 부담이 적은" 답으로 NAT Gateway를 고릅니다.

4.7 ENI, 퍼블릭 IP, Elastic IP

  • ENI(Elastic Network Interface): 가상 NIC. 사설 IP(주/보조), 퍼블릭 IP, MAC, 보안 그룹을 가짐. 같은 AZ의 다른 인스턴스로 옮겨 붙일 수 있음.
  • 자동 할당 퍼블릭 IP: 인스턴스 정지/시작 시 바뀜. 서브넷 설정 "퍼블릭 IPv4 자동 할당"으로 제어.
  • Elastic IP: 고정 공인 IP. 계정에 할당되어 다른 인스턴스로 재매핑 가능(장애 조치). 리전당 기본 5개.
  • Source/Destination Check: 기본 켜짐. 인스턴스가 자신의 IP가 아닌 트래픽을 송수신하면 차단 → NAT 인스턴스, 방화벽, VPN 어플라이언스는 꺼야 함.

4.8 VPC DNS 설정

  • enableDnsSupport: VPC+2 주소의 Amazon DNS(Route 53 Resolver) 사용 여부. 꺼지면 프라이빗 호스팅 영역·인터페이스 엔드포인트 DNS가 동작하지 않습니다.
  • enableDnsHostnames: 퍼블릭 IP가 있는 인스턴스에 퍼블릭 DNS 이름 부여. 인터페이스 엔드포인트의 프라이빗 DNS를 쓰려면 두 옵션 모두 켜야 합니다.
  • DHCP 옵션 세트로 도메인 이름, DNS 서버, NTP 서버를 지정할 수 있습니다.

4.9 기본 VPC

각 리전에는 172.31.0.0/16의 기본 VPC가 있으며, 모든 서브넷이 퍼블릭(/20)이고 IGW가 연결되어 있습니다. 빠른 테스트에는 편하지만 운영 환경에서는 사용하지 말고 직접 설계한 VPC를 사용하세요.
