5.1 VPC 엔드포인트

프라이빗 서브넷에서 S3, DynamoDB, SQS 같은 AWS 서비스를 쓸 때, 인터넷(NAT)을 거치지 않고 AWS 내부 네트워크로 직접 접근하게 해줍니다. 보안(인터넷 노출 없음)과 비용(NAT 처리 요금 절감) 두 가지 이점이 있습니다.

구분게이트웨이 엔드포인트인터페이스 엔드포인트 (PrivateLink)
지원 서비스S3, DynamoDB 두 개뿐대부분의 AWS 서비스 + 서드파티/자체 서비스 (S3도 지원)
동작 방식라우트 테이블에 프리픽스 리스트(pl-xxx) 경로 추가서브넷에 ENI(사설 IP) 생성, DNS로 해당 IP로 연결
비용무료AZ당 시간 요금 + GB당 요금
온프레미스/피어링에서 접근불가(라우팅 기반이라 VPC 내부 전용)가능(VPN/DX/TGW로 ENI IP에 도달)
보안 제어엔드포인트 정책엔드포인트 정책 + 보안 그룹
// S3 버킷 정책: 특정 VPC 엔드포인트를 통한 접근만 허용
{
  "Effect": "Deny", "Principal": "*", "Action": "s3:*",
  "Resource": ["arn:aws:s3:::secure-bucket", "arn:aws:s3:::secure-bucket/*"],
  "Condition": { "StringNotEquals": { "aws:SourceVpce": "vpce-0a1b2c3d" } }
}
⚠ 엔드포인트 사용 시 흔한 실수 • 게이트웨이 엔드포인트는 같은 리전의 S3에만 적용됩니다. 다른 리전 버킷은 여전히 NAT를 탑니다.
• 인터페이스 엔드포인트의 보안 그룹에서 클라이언트 → 443 인바운드를 허용하지 않아 타임아웃 나는 경우가 매우 흔합니다.
• 완전 격리 서브넷에서 SSM Session Manager를 쓰려면 ssm, ssmmessages, (필요 시 ec2messages) 인터페이스 엔드포인트가 필요합니다. ECR에서 이미지를 받으려면 ecr.api, ecr.dkr + S3 게이트웨이 엔드포인트가 필요합니다.

PrivateLink로 내 서비스 공개하기

서비스 제공자는 NLB(또는 GWLB) 앞에 엔드포인트 서비스를 만들고, 소비자는 자기 VPC에 인터페이스 엔드포인트를 만듭니다. 트래픽은 단방향(소비자 → 제공자)이고, 양쪽 CIDR이 겹쳐도 동작하며, VPC 전체를 연결하지 않고 특정 서비스만 노출한다는 점이 Peering과의 큰 차이입니다. SaaS 제공, 멀티 계정 공용 서비스에 많이 씁니다. 최근에는 VPC Lattice(서비스 간 L7 연결·인증 관리형 서비스)와 리소스 엔드포인트(RDS 등 특정 리소스를 NLB 없이 공유)도 선택지입니다.

5.2 VPC Peering

  • 두 VPC를 1:1로 연결. 같은/다른 계정, 같은/다른 리전 모두 가능. AWS 백본 사용, 대역폭 제한·단일 장애점 없음.
  • 전이적 라우팅 불가(Non-transitive): A–B, B–C가 피어링되어 있어도 A는 C와 통신할 수 없습니다. B의 IGW/NAT/VPN을 빌려 쓰는 것(edge-to-edge)도 불가.
  • CIDR이 겹치면 생성 불가.
  • 양쪽 라우트 테이블에 상대 CIDR → pcx-xxx 경로를 직접 추가해야 하고, 보안 그룹도 허용해야 합니다(같은 리전이면 상대 VPC의 SG ID 참조 가능).
  • VPC가 많아지면 연결 수가 n(n−1)/2로 폭증 → 10개 VPC면 45개. 이때 Transit Gateway를 씁니다.

5.3 Transit Gateway (TGW)

그림 5-1. 허브 앤 스포크: 모든 네트워크가 TGW 하나에 연결(Attachment)된다
개념설명
AttachmentTGW에 붙는 연결: VPC, VPN, Direct Connect Gateway, TGW Peering, Connect(GRE/BGP, SD-WAN 연동)
TGW 라우트 테이블TGW 내부의 라우팅 도메인. 여러 개 만들어 세그먼트 분리(예: Prod와 Dev는 서로 못 가고, 둘 다 Shared는 갈 수 있게)
AssociationAttachment가 "어느 라우트 테이블을 보고 나갈지" 결정 (Attachment당 1개)
PropagationAttachment의 CIDR을 어떤 라우트 테이블에 자동으로 전파(학습)할지 (여러 개 가능)
VPC Attachment 서브넷AZ마다 하나의 서브넷 지정(관례적으로 전용 /28). 지정한 AZ에서만 트래픽 처리 가능
Appliance Mode검사용 VPC(방화벽)에서 대칭 라우팅 보장 — 같은 흐름이 같은 AZ 방화벽을 지나게 함
성능VPC attachment당 AZ별 최대 100 Gbps 버스트, VPN 터널당 1.25 Gbps(ECMP로 묶어 확장)
💡 세그멘테이션 예시 RT-Prod: Prod VPC Attachment를 연결(Associate). 전파: Shared, 온프레미스(VPN/DX)
RT-Dev: Dev VPC Attachment 연결. 전파: Shared
RT-Shared: Shared VPC·VPN Attachment 연결. 전파: Prod, Dev, 온프레미스
→ Prod ↔ Dev는 서로의 경로가 없으므로 통신 불가. 블랙홀 경로(blackhole)로 명시적 차단도 가능.
VPC 쪽 라우트 테이블에도 10.0.0.0/8 → tgw-xxx 같은 경로를 넣어야 한다는 점을 잊지 마세요.

대규모 글로벌 네트워크는 AWS Cloud WAN(정책 기반으로 여러 리전의 TGW·세그먼트를 중앙 관리)을 고려합니다.

5.4 Site-to-Site VPN

구성 요소설명
CGW (Customer Gateway)온프레미스 VPN 장비의 정보(공인 IP, BGP ASN)를 AWS에 등록한 리소스
VGW (Virtual Private Gateway)VPC 하나에 붙는 AWS 측 VPN 종단점 (또는 TGW에 VPN을 붙임)
VPN 연결터널 2개(서로 다른 AWS 엔드포인트, 고가용성), IPsec(IKEv1/v2)
라우팅정적 라우팅 또는 BGP(동적, 권장) — BGP는 장애 시 자동 경로 전환
대역폭터널당 최대 1.25 Gbps (Large 터널 옵션 시 5 Gbps). TGW + ECMP로 여러 터널 합산
Accelerated VPNGlobal Accelerator 엣지를 통해 진입 → 원거리 지사 성능 개선 (TGW에서만)
  • VPC 라우트 테이블에서 라우트 전파(Route Propagation)를 켜면 VGW가 학습한 온프레미스 경로가 자동으로 들어옵니다.
  • 온프레미스 방화벽에서 UDP 500(IKE), UDP 4500(NAT-T), ESP(프로토콜 50)를 허용해야 합니다.
  • 터널이 유휴 상태면 내려갈 수 있으므로 DPD 설정 또는 지속적인 핑으로 유지합니다.
  • Client VPN: 개별 사용자 PC(OpenVPN 기반)가 VPC에 접속하는 관리형 원격 접속 VPN. 사이트 간 VPN과 구분하세요.

5.5 Direct Connect (DX)

온프레미스와 AWS를 전용 물리 회선으로 연결합니다. 인터넷을 거치지 않아 대역폭·지연이 일정하고, AWS에서 나가는 데이터 전송 비용이 인터넷보다 저렴합니다. 회선 개통에는 수 주가 걸릴 수 있습니다.

그림 5-2. Direct Connect 구성과 가상 인터페이스(VIF) 3종
개념설명
Dedicated ConnectionAWS와 직접 계약하는 물리 포트: 1, 10, 100, 400 Gbps
Hosted Connection파트너가 나눠 제공: 50 Mbps ~ 25 Gbps
VIF (Virtual Interface)802.1Q VLAN + BGP 세션. Private / Public / Transit 3종
Direct Connect Gateway글로벌 리소스. 하나의 DX로 여러 리전의 VPC(VGW) 또는 TGW에 연결
LAG같은 속도의 여러 연결을 묶음(LACP)
암호화DX는 기본 암호화가 아님 → MACsec(10/100/400G 전용 연결) 또는 DX 위에 IPsec VPN

DX 고가용성 설계 [ANS]

  • 최대 복원력: 2개 DX 로케이션 × 각 2개 연결(장비 분리).
  • 높은 복원력: 2개 DX 로케이션 × 각 1개 연결.
  • 비용 효율적 백업: DX 1개 + Site-to-Site VPN 백업. AWS는 같은 프리픽스라면 DX 경로를 VPN보다 우선합니다.

BGP 경로 선택 제어

목적방법
AWS → 온프레미스 방향 선택(인바운드 제어)더 구체적인 프리픽스 광고, AS_PATH Prepend(경로를 길게 보여 덜 선호되게)
온프레미스 → AWS 방향 선택(아웃바운드 제어)고객 라우터에서 Local Preference 조정
AWS 측 지역 선호도BGP Community 태그(7224:7100 낮음 ~ 7224:7300 높음)

AWS의 경로 우선순위(VPC 라우트 테이블): 가장 긴 프리픽스 → 정적 경로 → 전파된 경로 중 DX BGP → 정적 VPN → BGP VPN 순.

5.7 VPC Flow Logs

ENI 단위로 오가는 IP 트래픽의 메타데이터(패킷 내용 아님)를 CloudWatch Logs, S3, Firehose로 기록합니다. VPC/서브넷/ENI 수준에서 켤 수 있습니다.

# 기본 형식 (version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status)
2 123456789012 eni-0a1b 10.0.11.25 10.0.21.8 49152 3306 6 10 840 1700000000 1700000060 ACCEPT OK
2 123456789012 eni-0a1b 203.0.113.9 10.0.1.10 51515 22 6 1 40 1700000000 1700000060 REJECT OK
  • REJECT는 SG 또는 NACL이 막았다는 뜻. 인바운드는 ACCEPT인데 응답이 REJECT면 → NACL 아웃바운드(임시 포트)를 의심.
  • 기록되지 않는 트래픽: Amazon DNS 질의, 메타데이터(169.254.169.254), DHCP, Windows 라이선스 활성화, 기본 VPC 라우터 예약 IP 트래픽 등.
  • 사용자 지정 형식으로 pkt-srcaddr, tcp-flags, flow-direction, traffic-path 등 추가 가능 → NAT 뒤 실제 출발지 파악에 유용.
  • 분석은 CloudWatch Logs Insights 또는 S3 + Athena.

패킷 내용까지 봐야 한다면 Traffic Mirroring(ENI 트래픽을 IDS/분석 장비로 복사)을 사용합니다. 경로 문제를 정적으로 분석하려면 Reachability Analyzer(A→B 도달 가능 여부와 막는 지점 표시), 의도치 않은 외부 노출은 Network Access Analyzer를 씁니다.

5.8 IPv6 in VPC

  • VPC에 Amazon 제공 /56 또는 BYOIP/IPAM의 IPv6 CIDR 할당, 서브넷은 /64.
  • IPv6 주소는 모두 글로벌 유니캐스트(공인)입니다. NAT가 없으므로, 아웃바운드만 허용하려면 Egress-only Internet Gateway를 사용(IPv6용 NAT GW 역할).
  • IPv6 전용 서브넷 + DNS64/NAT64(NAT GW가 지원)로 IPv4 전용 서비스와 통신 가능.
  • 퍼블릭 IPv4 과금 이후 IPv6 도입이 비용 절감 수단으로 주목받고 있습니다. ALB/NLB는 듀얼 스택 지원.
