CHAPTER 0이 교재를 공부하는 방법

학습 순서

AWS는 서비스가 200개가 넘지만, 인프라 엔지니어가 반드시 알아야 할 핵심은 생각보다 적습니다. 이 교재는 "네트워크 → 권한(IAM) → VPC → 그 위에 올라가는 서비스" 순서로 구성되어 있습니다. 이유는 간단합니다. AWS에서 장애·보안사고·연결 문제의 80% 이상은 네트워크 설정과 권한 설정에서 발생하기 때문입니다.

단계범위목표 기간(권장)
1. 기초 다지기0~3장: 클라우드 개념, 네트워크 기초, IAM1~2주
2. 네트워크 핵심4~5장: VPC 기본/심화 — 가장 중요, 그림을 직접 그려보며 학습2~3주
3. 서비스 이해6~13장: 컴퓨팅, LB, 스토리지, DB, DNS/CDN, 보안, 모니터링, 통합3~4주
4. 자동화·설계14~15장: IaC, 고가용성/DR, 비용1~2주
5. 실전16~17장: 직접 구축하고 일부러 망가뜨려 보며 트러블슈팅1~2주

실습 계정 준비 & 비용 사고 방지

  1. 루트 계정 보호: 가입 직후 루트 계정에 MFA를 설정하고, 루트 액세스 키는 절대 만들지 않습니다. 일상 작업은 IAM Identity Center 사용자(또는 IAM 사용자)로 합니다.
  2. 예산 알림(AWS Budgets): 월 예산(예: 10 USD)을 만들고 80%/100% 도달 시 이메일 알림을 받도록 설정합니다.
  3. 프리 티어 확인: 프리 티어 범위는 계정 생성 시점에 따라 다릅니다(2025년 7월 이후 신규 계정은 크레딧 기반 모델). Billing 콘솔에서 본인 계정 조건을 확인하세요.
  4. 비싼 "숨은 비용" 주의: NAT Gateway(시간당 + GB당 과금), 퍼블릭 IPv4 주소(2024년 2월부터 사용 중인 모든 퍼블릭 IPv4에 시간당 과금), 켜놓은 RDS/EKS 클러스터, 삭제하지 않은 EBS 스냅샷, Elastic IP 미연결 상태.
  5. 실습 후 정리: 실습 리소스는 태그(Project=study)를 붙이고, 끝나면 Terraform/CloudFormation으로 한 번에 삭제하는 습관을 들입니다.
⚠ 경고: 액세스 키 유출GitHub 등 공개 저장소에 액세스 키를 올리면 수 분 안에 봇이 탐지해 채굴용 인스턴스를 대량으로 띄웁니다. 키는 코드에 넣지 말고, 가능하면 장기 키 대신 IAM 역할·SSO(임시 자격 증명)를 사용하세요.

CHAPTER 1클라우드와 AWS 개요

학습 목표 · 클라우드 서비스 모델을 구분한다 · 리전/가용 영역/엣지 로케이션의 차이와 선택 기준을 설명한다 · 공동 책임 모델로 "누가 무엇을 지키는지" 판단한다 · Well-Architected 6대 원칙을 안다

1.1 클라우드 컴퓨팅이란

클라우드 컴퓨팅은 컴퓨팅 자원(서버, 스토리지, 네트워크, DB 등)을 인터넷을 통해 필요할 때 빌려 쓰고 쓴 만큼 비용을 내는 모델입니다. 온프레미스(자체 데이터센터)와 비교하면 다음과 같은 차이가 있습니다.

항목온프레미스클라우드(AWS)
초기 비용서버·랙·네트워크 장비 구매(CAPEX)없음, 사용량 기반(OPEX)
용량 계획최대 피크 기준으로 미리 구매 → 유휴 자원 발생수요에 따라 자동 확장/축소(Auto Scaling)
구축 속도장비 조달에 수 주~수 개월수 분
글로벌 확장해외 IDC 계약 필요리전 선택만으로 즉시
책임 범위물리 보안부터 애플리케이션까지 전부공동 책임 모델에 따라 분담

서비스 모델: IaaS / PaaS / SaaS

모델사용자가 관리AWS가 관리AWS 예시
IaaSOS, 런타임, 앱, 데이터, 네트워크 설정물리 서버, 하이퍼바이저, 데이터센터EC2, VPC, EBS
PaaS애플리케이션 코드, 데이터OS 패치, 런타임, 확장Elastic Beanstalk, RDS, Lambda(FaaS)
SaaS사용 설정, 데이터전부Amazon WorkMail, QuickSight

배포 모델은 퍼블릭 클라우드, 프라이빗 클라우드, 그리고 둘을 연결한 하이브리드 클라우드(VPN/Direct Connect로 온프레미스와 AWS 연결)가 있습니다.

1.2 AWS 글로벌 인프라

그림 1-1. 리전 – 가용 영역(AZ) – 데이터센터의 관계와 엣지 인프라

리전(Region)

리전은 지리적으로 분리된 지역으로, 최소 3개 이상의 가용 영역으로 구성됩니다. 리전끼리는 완전히 독립되어 있어, 데이터는 사용자가 명시적으로 복제하지 않는 한 리전을 벗어나지 않습니다(데이터 주권). 한국에는 ap-northeast-2(서울) 리전이 있으며 4개의 AZ를 제공합니다.

리전 선택 기준 4가지

  1. 규정 준수: 개인정보·금융 데이터의 국외 이전 제한(데이터 주권)
  2. 지연 시간: 사용자와 가까운 리전일수록 응답이 빠름
  3. 서비스 가용성: 신규 서비스는 일부 리전에서 먼저 출시됨
  4. 가격: 리전별로 단가가 다름(일반적으로 us-east-1이 저렴한 편)

가용 영역(Availability Zone, AZ)

AZ는 하나 이상의 독립된 데이터센터 묶음입니다. 고가용성의 기본 단위이며, 운영 서비스는 반드시 2개 이상의 AZ에 분산 배치해야 합니다.

⚠ AZ 이름 ≠ 물리 위치ap-northeast-2a라는 이름은 계정마다 실제 물리 AZ에 다르게 매핑될 수 있습니다(특정 AZ에 부하가 몰리는 것을 막기 위해). 여러 계정 간에 같은 물리 AZ를 맞춰야 할 때는 AZ ID(예: apne2-az1)를 사용하세요. aws ec2 describe-availability-zones로 확인할 수 있습니다.

글로벌 서비스 vs 리전 서비스

범위서비스
글로벌IAM, Route 53, CloudFront, WAF(CloudFront용), Organizations, Global Accelerator
리전VPC, S3(버킷은 리전에 생성되지만 이름은 전 세계 고유), DynamoDB, Lambda, ELB, RDS 등 대부분
AZEC2 인스턴스, EBS 볼륨, 서브넷, NAT Gateway(존 단위)

1.3 공동 책임 모델 (Shared Responsibility Model)

AWS는 "클라우드 의 보안(Security OF the cloud)", 고객은 "클라우드 안에서의 보안(Security IN the cloud)"을 책임집니다.

AWS 책임고객 책임
데이터센터 물리 보안, 하드웨어, 하이퍼바이저, 글로벌 네트워크 인프라, 관리형 서비스의 OS 패치(RDS, Lambda 등)IAM 권한 관리, 데이터 암호화 설정, 보안 그룹/NACL, EC2 게스트 OS 패치, 애플리케이션 보안, 백업 정책

서비스가 관리형(추상화)일수록 고객 책임이 줄어듭니다. 예를 들어 EC2에서는 OS 패치가 고객 몫이지만, RDS에서는 AWS가 DB 엔진 패치를 수행합니다(시점 선택은 고객). 하지만 데이터와 접근 권한은 어떤 서비스에서도 항상 고객 책임입니다.

2.2 IPv4 주소와 CIDR

IPv4 주소는 32비트이며 8비트씩 4개로 나눠 10.0.1.25처럼 표기합니다. CIDR(Classless Inter-Domain Routing) 표기 10.0.0.0/16에서 /16은 "앞의 16비트가 네트워크 부분"이라는 뜻입니다. 나머지 16비트가 호스트 부분이므로 216 = 65,536개의 주소를 가집니다.

10.0.0.0/16
  10       .0        .0        .0
  00001010 .00000000 | 00000000 .00000000
  └──── 네트워크 16비트 ────┘ └── 호스트 16비트 ──┘
  범위: 10.0.0.0 ~ 10.0.255.255  (65,536개)
서브넷 마스크로는 255.255.0.0

자주 쓰는 프리픽스 크기

CIDR주소 수AWS 서브넷에서 사용 가능용도 예시
/1665,53665,531VPC 최대 크기
/204,0964,091기본 VPC의 서브넷, EKS 파드용 큰 서브넷
/221,0241,019프라이빗 앱 서브넷
/24256251일반적인 서브넷
/266459DB, 엔드포인트 서브넷
/281611AWS 서브넷 최소 크기, TGW 연결 서브넷
/321—단일 호스트(보안 그룹 규칙에서 특정 IP 지정)

공식: 주소 수 = 2(32 − 프리픽스). 프리픽스가 1 커지면 크기는 절반이 됩니다.

사설 IP 대역 (RFC 1918)

대역범위비고
10.0.0.0/810.0.0.0 – 10.255.255.255가장 큼, 대규모 기업망에서 주로 사용
172.16.0.0/12172.16.0.0 – 172.31.255.255AWS 기본 VPC가 172.31.0.0/16 사용
192.168.0.0/16192.168.0.0 – 192.168.255.255가정용 공유기에서 흔함 → VPN 충돌 주의

그 밖에 100.64.0.0/10(CGNAT, RFC 6598)도 VPC 보조 CIDR로 쓸 수 있으며, EKS에서 파드 IP 고갈 문제 해결용으로 자주 활용됩니다. 169.254.0.0/16은 링크 로컬로, AWS에서는 169.254.169.254(인스턴스 메타데이터), 169.254.169.253(DNS) 등에 쓰입니다.

서브넷팅 실전 계산

문제: 10.10.0.0/16 VPC를 3개 AZ × (퍼블릭, 프라이빗 앱, 프라이빗 DB) = 9개 서브넷으로 나누되, 앱 서브넷을 가장 크게 하고 싶다.

# 앱 서브넷: /20 (4,096개) × 3
10.10.0.0/20    app-a   (10.10.0.0  ~ 10.10.15.255)
10.10.16.0/20   app-b   (10.10.16.0 ~ 10.10.31.255)
10.10.32.0/20   app-c   (10.10.32.0 ~ 10.10.47.255)
# 퍼블릭 서브넷: /24 (256개) × 3 — LB, NAT GW 정도만 들어가므로 작게
10.10.48.0/24   pub-a
10.10.49.0/24   pub-b
10.10.50.0/24   pub-c
# DB 서브넷: /24 × 3
10.10.52.0/24   db-a
10.10.53.0/24   db-b
10.10.54.0/24   db-c
# 10.10.64.0/18 이후는 미래 확장용으로 비워둠 (중요!)
💡 서브넷 경계 빠르게 계산하기/20의 블록 크기는 3번째 옥텟 기준 2(24−20) = 16입니다. 그래서 0, 16, 32, 48 …에서 시작합니다. /22면 4씩(0, 4, 8, …), /26이면 4번째 옥텟 기준 64씩(0, 64, 128, 192)입니다. 시작 주소가 블록 크기의 배수가 아니면 잘못된 CIDR입니다(예: 10.0.5.0/22는 무효, 10.0.4.0/22가 맞음).

2.3 라우팅의 원리

라우터(그리고 AWS 라우트 테이블)는 패킷의 목적지 IP를 보고 다음 홉(next hop)을 결정합니다. 여러 경로가 일치하면 가장 긴 접두사 일치(Longest Prefix Match) 규칙에 따라 더 구체적인 경로가 이깁니다.

라우트 테이블:
  10.0.0.0/16     → local
  10.1.0.0/16     → pcx-1234 (VPC Peering)
  10.1.5.0/24     → tgw-abcd (Transit Gateway)
  0.0.0.0/0       → igw-9999

목적지 10.1.5.7  → 10.1.0.0/16 과 10.1.5.0/24 둘 다 일치 → /24가 더 길므로 TGW로
목적지 8.8.8.8   → 0.0.0.0/0 만 일치 → 인터넷 게이트웨이로
목적지 10.0.3.4  → local (VPC 내부 통신)

0.0.0.0/0은 "모든 주소"를 뜻하는 기본 경로(default route)입니다. 프리픽스 길이가 0이라 항상 가장 마지막 순위입니다.

2.4 NAT (Network Address Translation)

사설 IP는 인터넷에서 라우팅되지 않으므로, 사설 IP를 가진 서버가 인터넷에 나가려면 공인 IP로 바꿔주는 장치가 필요합니다.

  • SNAT / PAT: 여러 사설 IP를 하나의 공인 IP로 변환(포트로 구분). AWS의 NAT Gateway가 이 역할 → 프라이빗 서브넷의 아웃바운드 인터넷 접근.
  • 1:1 NAT: 사설 IP 하나와 공인 IP 하나를 고정 매핑. AWS의 인터넷 게이트웨이(IGW)가 퍼블릭 IP/EIP를 가진 인스턴스에 대해 이 역할을 수행합니다. 인스턴스 OS 안에서는 공인 IP가 보이지 않고 사설 IP만 보이는 이유가 이것입니다.

2.6 DNS

2.7 HTTP와 TLS

HTTPS = HTTP + TLS. TLS는 서버 인증서로 서버 신원을 검증하고, 세션 키를 교환해 트래픽을 암호화합니다. AWS에서는 ACM(무료 공인 인증서)을 ALB·CloudFront·API Gateway에 붙여 TLS를 종료하는 것이 일반적입니다. SNI(Server Name Indication) 덕분에 하나의 ALB 리스너에 여러 도메인의 인증서를 붙일 수 있습니다.
