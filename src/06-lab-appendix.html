CHAPTER 16실습: 3-Tier 웹 아키텍처 구축

학습 목표 · 지금까지 배운 리소스를 직접 엮어 동작하는 서비스를 만든다 · 패킷이 어떤 리소스를 거치는지 한 홉씩 설명한다 · 실습 후 모든 리소스를 정리한다

16.1 목표 아키텍처

사용자 ──HTTPS──▶ Route 53 (app.example.com, Alias)
                    │
                    ▼
               CloudFront (+ WAF)        ← 선택 사항
                    │
                    ▼
     ALB (퍼블릭 서브넷 a/c, sg-alb: 443 from 0.0.0.0/0)
                    │  HTTP 8080
                    ▼
     ASG: EC2 (프라이빗 앱 서브넷 a/c, sg-app: 8080 from sg-alb)
        │ 아웃바운드 업데이트 → NAT GW(같은 AZ) → IGW
        │ S3 접근 → 게이트웨이 엔드포인트
        │ 3306
        ▼
     RDS MySQL Multi-AZ (프라이빗 DB 서브넷 a/c, sg-db: 3306 from sg-app)
운영 접속: SSM Session Manager (SSH 포트 없음, 배스천 없음)

16.2 단계별 CLI 실습

아래 명령은 흐름 이해를 위한 것입니다. 반복 실습은 14장의 Terraform 코드로 하는 것을 권장합니다. ID 값은 앞 단계 출력에서 받아 변수에 저장합니다.

1단계: VPC와 서브넷

export AWS_DEFAULT_REGION=ap-northeast-2
VPC=$(aws ec2 create-vpc --cidr-block 10.0.0.0/16 \
  --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=lab-vpc}]' \
  --query Vpc.VpcId --output text)
aws ec2 modify-vpc-attribute --vpc-id $VPC --enable-dns-hostnames
mk() { aws ec2 create-subnet --vpc-id $VPC --cidr-block $1 --availability-zone $2 \
       --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=$3}]" \
       --query Subnet.SubnetId --output text; }
PUB_A=$(mk 10.0.1.0/24  ap-northeast-2a pub-a);  PUB_C=$(mk 10.0.2.0/24  ap-northeast-2c pub-c)
APP_A=$(mk 10.0.11.0/24 ap-northeast-2a app-a);  APP_C=$(mk 10.0.12.0/24 ap-northeast-2c app-c)
DB_A=$(mk 10.0.21.0/24  ap-northeast-2a db-a);   DB_C=$(mk 10.0.22.0/24  ap-northeast-2c db-c)

2단계: 인터넷 게이트웨이와 퍼블릭 라우팅

IGW=$(aws ec2 create-internet-gateway --query InternetGateway.InternetGatewayId --output text)
aws ec2 attach-internet-gateway --internet-gateway-id $IGW --vpc-id $VPC
RT_PUB=$(aws ec2 create-route-table --vpc-id $VPC --query RouteTable.RouteTableId --output text)
aws ec2 create-route --route-table-id $RT_PUB --destination-cidr-block 0.0.0.0/0 --gateway-id $IGW
aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $PUB_A
aws ec2 associate-route-table --route-table-id $RT_PUB --subnet-id $PUB_C

3단계: NAT Gateway와 프라이빗 라우팅 (AZ별)

for AZ in A C; do
  PUB=$(eval echo \$PUB_$AZ); APP=$(eval echo \$APP_$AZ)
  EIP=$(aws ec2 allocate-address --domain vpc --query AllocationId --output text)
  NAT=$(aws ec2 create-nat-gateway --subnet-id $PUB --allocation-id $EIP \
        --query NatGateway.NatGatewayId --output text)
  aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT
  RT=$(aws ec2 create-route-table --vpc-id $VPC --query RouteTable.RouteTableId --output text)
  aws ec2 create-route --route-table-id $RT --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT
  aws ec2 associate-route-table --route-table-id $RT --subnet-id $APP
done
# DB 서브넷은 별도 라우트 테이블(기본 경로 없음) = 격리 서브넷

4단계: 보안 그룹 체이닝

sg() { aws ec2 create-security-group --group-name $1 --description $1 --vpc-id $VPC \
       --query GroupId --output text; }
SG_ALB=$(sg lab-alb); SG_APP=$(sg lab-app); SG_DB=$(sg lab-db)
aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 80  --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SG_ALB --protocol tcp --port 443 --cidr 0.0.0.0/0
aws ec2 authorize-security-group-ingress --group-id $SG_APP --protocol tcp --port 8080 --source-group $SG_ALB
aws ec2 authorize-security-group-ingress --group-id $SG_DB  --protocol tcp --port 3306 --source-group $SG_APP

5단계: 앱 서버 (Launch Template + ASG)

# 사전 준비: AmazonSSMManagedInstanceCore 정책이 붙은 역할 + 인스턴스 프로파일 "lab-ec2"
AMI=$(aws ssm get-parameter --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 \
      --query Parameter.Value --output text)
cat > userdata.sh <<'EOF'
#!/bin/bash
dnf -y install python3
mkdir -p /srv && cd /srv
echo "ok from $(hostname)" > health
echo "hello from $(hostname)" > index.html
nohup python3 -m http.server 8080 &
EOF
aws ec2 create-launch-template --launch-template-name lab-lt --launch-template-data "{
  \"ImageId\":\"$AMI\",\"InstanceType\":\"t4g.micro\",
  \"IamInstanceProfile\":{\"Name\":\"lab-ec2\"},
  \"SecurityGroupIds\":[\"$SG_APP\"],
  \"MetadataOptions\":{\"HttpTokens\":\"required\"},
  \"UserData\":\"$(base64 -w0 userdata.sh)\"}"

6단계: ALB와 대상 그룹

TG=$(aws elbv2 create-target-group --name lab-tg --protocol HTTP --port 8080 --vpc-id $VPC \
     --health-check-path /health --query 'TargetGroups[0].TargetGroupArn' --output text)
ALB=$(aws elbv2 create-load-balancer --name lab-alb --subnets $PUB_A $PUB_C \
      --security-groups $SG_ALB --query 'LoadBalancers[0].LoadBalancerArn' --output text)
aws elbv2 create-listener --load-balancer-arn $ALB --protocol HTTP --port 80 \
  --default-actions Type=forward,TargetGroupArn=$TG
# (도메인이 있다면) ACM 인증서 발급 후 443 리스너 추가, 80은 리다이렉트로 변경
aws autoscaling create-auto-scaling-group --auto-scaling-group-name lab-asg \
  --launch-template LaunchTemplateName=lab-lt --min-size 2 --max-size 4 --desired-capacity 2 \
  --vpc-zone-identifier "$APP_A,$APP_C" --target-group-arns $TG \
  --health-check-type ELB --health-check-grace-period 120
aws autoscaling put-scaling-policy --auto-scaling-group-name lab-asg --policy-name cpu50 \
  --policy-type TargetTrackingScaling --target-tracking-configuration \
  '{"PredefinedMetricSpecification":{"PredefinedMetricType":"ASGAverageCPUUtilization"},"TargetValue":50}'

7단계: 확인

DNS=$(aws elbv2 describe-load-balancers --load-balancer-arns $ALB --query 'LoadBalancers[0].DNSName' --output text)
for i in 1 2 3 4; do curl -s http://$DNS/; done        # 두 호스트 이름이 번갈아 나오면 성공
aws elbv2 describe-target-health --target-group-arn $TG  # healthy 확인

RDS(8단계)는 aws rds create-db-subnet-group(DB_A, DB_C) → aws rds create-db-instance --multi-az --no-publicly-accessible --vpc-security-group-ids $SG_DB --manage-master-user-password(비밀번호를 Secrets Manager가 관리) 순으로 생성합니다.

16.3 패킷 흐름 따라가기 (면접 단골 질문)

ℹ 사용자 요청 한 건이 거치는 경로 ① 브라우저가 app.example.com 조회 → Route 53이 ALB의 IP들 반환(Alias)
② 클라이언트 → ALB 퍼블릭 IP:80. 인터넷에서 IGW가 목적지 공인 IP를 ALB 노드 ENI의 사설 IP로 변환
③ 퍼블릭 서브넷 NACL 인바운드 평가 → sg-alb 인바운드 443/80 허용
④ ALB가 대상 선택(헬스 체크 정상인 인스턴스). 새 TCP 연결: 출발지 = ALB 노드 사설 IP, 목적지 = 10.0.11.x:8080
⑤ VPC 라우트 테이블 local 경로 → 앱 서브넷 NACL 인바운드 → sg-app(소스 sg-alb, 8080 허용)
⑥ 앱이 DB 조회: 10.0.11.x → 10.0.21.y:3306, local 경로, sg-db(소스 sg-app) 허용
⑦ 응답은 역순. SG는 상태 저장이라 자동 허용, NACL은 임시 포트 아웃바운드 규칙 필요
⑧ 앱 서버가 OS 업데이트 시: 0.0.0.0/0 → 같은 AZ NAT GW(사설 IP를 EIP로 SNAT) → IGW → 인터넷

16.4 일부러 망가뜨려 보기 (트러블슈팅 훈련)

이렇게 바꿔보세요예상 증상 / 확인할 것
sg-app의 소스를 sg-alb → 다른 SG로 변경대상 unhealthy → ALB 503, Flow Logs에 REJECT
앱 서브넷 NACL에 아웃바운드 1024-65535 거부헬스 체크 실패(응답이 못 나감)
app-a 라우트 테이블에서 NAT 경로 삭제app-a 인스턴스만 dnf update 타임아웃, SSM 접속도 실패(엔드포인트가 없다면)
헬스 체크 경로를 /nope으로모든 대상 unhealthy (404) → 503
인스턴스 하나에서 웹 서버 프로세스 종료ELB 헬스 체크 유형이면 ASG가 자동 교체

Reachability Analyzer로 "ALB ENI → 인스턴스 ENI:8080" 경로를 분석해 어느 구성 요소가 막는지 확인해 보세요.

17.1 연결 문제 진단 순서 (바깥에서 안으로, 아래에서 위로)

  1. DNS: 이름이 올바른 IP로 풀리나? dig app.example.com, 프라이빗 호스팅 영역이 VPC에 연결되었나?
  2. 라우팅: 출발지 서브넷 라우트 테이블에 목적지 경로가 있나? 돌아오는 경로도 있나(비대칭 라우팅)? Peering/TGW는 양쪽 모두 경로 필요.
  3. NACL: 양쪽 서브넷, 양방향(임시 포트 포함) 허용인가?
  4. 보안 그룹: 목적지 인바운드 허용? 출발지 아웃바운드 허용(기본 전체 허용을 지웠다면)?
  5. 대상 OS: 프로세스가 0.0.0.0에서 리슨 중인가(127.0.0.1만 리슨하면 외부 불가)? OS 방화벽(firewalld/iptables)?
  6. 애플리케이션: 로그, 헬스 체크 응답 코드.

17.2 증상별 체크리스트

증상1순위 의심

F. 확인 문제 정답

1장

1) 최소 2개 AZ에 분산 배치(ELB + ASG 등). 2) EC2 위 MySQL은 고객, RDS는 AWS가 엔진 패치(적용 시점·유지 관리 기간 설정은 고객). 3) AZ 이름이 아닌 AZ ID(apne2-az1 등).

2장

1) 1,024개, 사용 가능 1,019개. 2) 10.0.8.0/21은 올바름(8의 배수), 10.0.12.0/21은 무효(/21의 시작은 0, 8, 16…). 3) 더 긴 /16이 이기므로 pcx(피어링). 4) 안 됨. 응답은 클라이언트의 임시 포트로 나가야 하므로 아웃바운드 1024-65535 허용 필요.

3장

1) 불가 — 명시적 Deny 우선. 2) (a) Lambda 실행 역할에 s3:GetObject 허용 + 계정 B 버킷 정책에서 계정 A의 역할 허용, (b) 계정 B에 읽기 역할을 만들고 Lambda가 AssumeRole. (KMS 암호화면 키 정책도) 3) 불가 — SCP는 권한을 주지 않으며 Allow가 별도로 필요.

4장

1) 안 됨 — 퍼블릭 IP/EIP 필요. 2) AZ-a 장애 시 모든 프라이빗 서브넷의 아웃바운드가 끊기고, 다른 AZ에서 AZ 간 전송 요금 발생 → AZ별 NAT GW(또는 리전 NAT GW). 3) NACL — SG는 거부 규칙이 없음. 4) 앱 서버의 보안 그룹 ID.

5장

1) A–C를 직접 피어링하거나 Transit Gateway 사용(피어링은 전이 불가). 2) S3 게이트웨이 엔드포인트(무료) 추가. 3) Route 53 Resolver 인바운드 엔드포인트 + 온프레미스 DNS에 조건부 전달 설정(+ VPN/DX 연결). 4) Direct Connect.

6장

1) 스팟 인스턴스(여러 인스턴스 유형, 체크포인트). 2) 스냅샷 생성 → AZ-c에서 볼륨 복원 → 연결. 3) ASG 헬스 체크 유형이 ELB인지, 대상 그룹 헬스 체크 설정. 4) Lambda를 프라이빗 서브넷에 두고 NAT GW 경로 설정(퍼블릭 서브넷에 둬도 퍼블릭 IP를 받지 못함).

8장

1) 0~30일 Standard → 30일 Standard-IA(또는 Glacier IR) → 365일 Glacier Flexible/Deep Archive → 7년(2,555일) 후 만료 삭제. 2) EFS. 3) CloudFront + OAC + ACM 인증서, 버킷은 퍼블릭 액세스 차단 유지.

9장

1) 아니요 — Multi-AZ 스탠바이는 읽기 불가(인스턴스 배포 기준). 읽기 전용 복제본 또는 Aurora 리더로 분리. 2) Aurora Global Database(또는 DynamoDB Global Tables). 3) RDS Proxy.

마치며AWS 네트워크를 잘 아는 엔지니어와 그렇지 않은 엔지니어의 차이는 결국 "패킷 하나가 어디를 거쳐 어떻게 돌아오는지 설명할 수 있는가"입니다. 16장의 패킷 흐름을 보지 않고 설명할 수 있을 때까지 반복해 보세요. 서비스의 세부 수치(한도, 가격, 성능)는 자주 바뀌므로, 원리를 이해하고 숫자는 공식 문서에서 확인하는 습관을 들이세요.
